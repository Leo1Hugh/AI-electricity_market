# 协作协议：GitHub 作为唯一交付总线

> 目标：两个 ChatGPT 账号（W1/W2）彼此看不到对方上下文，也不共享聊天记录。
> 解决办法不是"多贴几段话"，而是：**仓库是共享记忆，PR 是交付物，CI 是裁判，Lead 是唯一合并人。**

---

## 1. 角色

| 角色 | 是谁 | 权限 | 职责 |
| --- | --- | --- | --- |
| Lead | 本会话的统筹 agent | main 合并、契约、Issue 裁决 | 冻结契约、拆任务、验收、红队、最终选型 |
| W1 | ChatGPT Plus 账号 A | 写 w1/* 分支，开 PR | 数据管道、面板、特征、提交脚本 |
| W2 | ChatGPT Plus 账号 B | 写 w2/* 分支，开 PR | 模型、回测、集成、稳健性 |
| Human | 你 | repo owner | 建仓/授权、转发失败日志、拍板资源 |

**W1 与 W2 不直接对话。** 所有跨模块需求通过 Issue（标签 contract-change / dependency）表达，由 Lead 转成任务书。

---

## 2. 仓库与分支

- 仓库：**https://github.com/Leo1Hugh/AI-electricity_market**
- 默认分支：**main**（保护分支，禁止直接 push）
- 契约 tag：**contract-v1.0.0**（W1/W2 都从这里开分支）
- 工作分支：
  - **w1/r1-panel**：面板构建器
  - **w2/r1-harness**：回测骨架与基线
  - 后续：w1/r2-fetch、w2/r2-models、w1/r3-submit、w2/r3-ensemble……

分支命名：**w<编号>/r<轮次>-<主题>**，全小写，短横线。

---

## 3. 一个任务的完整生命周期

1. Lead 在 **docs/tasks/<TASK>.md** 写任务书，并在 **docs/任务看板.md** 登记。
2. Lead 从 contract tag 开分支（或由 W 自己开，但必须基于 tag）。
3. W 读：AGENTS.md → 建模契约 → 本协议 → 任务书。
4. W 在分支上实现，本地跑 **pytest -q** 和任务书里的 CLI。
5. W push 分支，开 PR 到 main。PR 标题：**[W1-R1] panel builder**。
6. CI 自动跑 pytest；红则 W 修，直到绿。
7. Lead review：看 diff、跑验收、查泄漏、查是否越界改文件。
8. Lead 合并（squash merge），打 tag（如需要），在任务看板更新状态。
9. 若 W 不能直接写 GitHub：走第 8 节的 Bundle 兜底，由 Human 代提交。

**一个 PR 只做一个任务。** 不允许"顺手重构"。


没有"结果" section 的 PR 视为未完成。

## 5. CI 与合并门

- CI 文件：**.github/workflows/ci.yml**
- 触发：所有 PR 到 main；main 的 push。
- 步骤：Python 3.11 → pip install -r requirements.txt → pytest -q。
- 合并门（Lead 人工确认）：
  1. CI 绿；
  2. 只改任务书列出的文件；
  3. 无敏感文件（pdf/docx/证件/token）；
  4. 测试里有**能推翻结论的断言**，不是只跑通；
  5. 报告里的数字有命令可复现。

## 6. 上下文隔离怎么解决

聊天上下文不共享，但以下东西共享：

| 共享物 | 位置 | 作用 |
| --- | --- | --- |
| 契约 | docs/建模契约_v1.md + src/em/contracts.py | 字段、公式、API 的唯一真源 |
| 任务书 | docs/tasks/*.md | 每次只读自己那一份 |
| 决策记录 | DECISIONS.md | 为什么这样定，避免重复争论 |
| 事故记录 | ERROR_LOG.md | 踩过的坑 + 抓住它的不变量 |
| 看板 | docs/任务看板.md | 当前谁在做什么、卡在哪 |
| PR | GitHub | 代码、测试、结果、讨论都在这里 |
| CI | GitHub Actions | 不依赖人复述的自动裁判 |

**规则**：任务消息里不复制大段契约；只给"读哪个文件 + 本次任务号"。
如果 W 不能读仓库，才使用 Lead 生成的自包含 prompt（prompts/generated/*.md）。

## 8. Bundle 兜底（W 不能写 GitHub 时）

如果账号只有只读连接器，或完全不能访问仓库：

1. W 在回复开头写 **MODE=B**。
2. 按以下格式输出完整文件，不要省略、不要用 "..."：

~~~text
<<<FILE src/em/data/panel.py>>>
<完整文件内容>
<<<END>>>
<<<FILE tests/test_panel_contract.py>>>
<完整文件内容>
<<<END>>>
~~~

3. Human 把整段回复保存为 **inbox/<TASK>.md**，运行：

~~~powershell
python scripts/apply_bundle.py inbox/W1-R1.md
~~~

4. 脚本只允许写 src/ tests/ scripts/ configs/，拒绝绝对路径和 ..
5. 之后由 Human 在 GitHub 网页或本地 git 提交到对应分支。

**优先 Mode G（直接 PR）；Mode B 只是降级方案。**

---

## 9. 安全与隐私

- 仓库是 **public**。证件、报名表、成绩单、token、.env、个人绝对路径**绝对不入库**。
- .gitignore 已屏蔽 *.pdf / *.docx / *身份证* / *研究生证*；不要用 git add -f 绕过。
- PR 里不要贴本机绝对路径（E:\...），用仓库相对路径。
- 不在代码里硬编码 token；CI 用 GitHub Secrets。
- 发现敏感文件已入库：立即告诉 Lead，停止 push，走历史清理流程。

---

## 10. 冲突与升级

| 情况 | 处理 |
| --- | --- |
| 两个 W 改了同一文件 | Lead 在合并前发现，后合并者 rebase；契约文件只有 Lead 能改 |
| W 需要新特征 | 开 Issue 标签 feature-request；Lead 决定是否进 v1.1 契约 |
| W 发现契约错误 | 开 Issue 标签 contract-change；不要自行修改 |
| CI 因环境失败 | 先复现；Lead 判断是代码还是环境；不要用 skip 掩盖 |
| 截止前 48 小时 | 只允许 bugfix，不允许新模型/新特征 |
